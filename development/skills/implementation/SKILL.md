# Implementation

一度にFeature全体を作らず、Task単位でBuild、Test、Verifyを繰り返す。仕様や計画が不足し、実装判断が変わる場合は先に確認する。

## 進め方

1. 対象Task、仕様、設計、受け入れ条件、既存規約、作業ツリーの状態を確認する。
2. 最小の垂直スライスを選び、変更前に検証コマンドと安全な停止点を決める。
3. TDDが適用できる振る舞いは`tdd`のREDから始める。
4. 既存のModuleとInterfaceを利用し、Scope内の最小変更を行う。新しい依存、Schema、CI、公開Contractなど影響の大きい変更は承認境界を確認する。
5. スライスごとに対象Test、型検査、Lint、Buildなど必要な検証を行い、Greenな状態で次へ進む。
6. 未完成機能が利用者へ露出する場合は、Feature flag、安全なDefault、Rollback可能な移行を設計する。
7. TaskのAcceptance criteriaと差分を照合し、仕様、文書、Testの更新漏れを確認する。

エラーが発生したら変更を重ね続けず、再現可能な状態を保存して`debugging`へ切り替える。

## 完了条件

- 対象TaskのAcceptance criteriaを満たす証拠がある。
- 変更は小さく、レビュー可能で、関連する検証が通っている。
- 仕様外の変更と利用者の既存変更を混ぜていない。
- 実施済み、未実施、未確認、残るリスクを分けて報告している。
