# Documentation

文書を実装後に一括生成せず、仕様、Domain model、Architecture、Code、Testの変更と同じ時点で更新する。既存の文書配置と形式を先に確認する。

## 進め方

1. 対象読者と、その人が文書を読んで行う判断または操作を定義する。
2. 現行の仕様、実装、コマンド、設定、Test結果を根拠として集める。確認できない主張は未確認とする。
3. READMEはQuick start、主要Commands、Architectureへの入口、検証方法を簡潔に保ち、設定から容易に分かる情報を重複させない。
4. 用語集はDomain用語と定義だけを保ち、実装詳細や一時メモを入れない。用語の矛盾は具体例で解消する。
5. ADRは、後戻りが高価、理由が将来分かりにくい、実際のTrade-offがある、の3条件を満たす場合だけ作る。Context、Decision、Alternatives、Consequences、Statusを記録する。
6. Inline commentは「なぜ」を説明する場合に限定し、コードが既に示す「何を」を繰り返さない。
7. Link、Command、Example、表示を実物で確認し、変更内容と未確認事項を記録する。

## 完了条件

- 文書の主張が現行の仕様または実装と一致する。
- 利用者が必要な入口と次の行動を見つけられる。
- 同じ判断が複数文書へ重複していない。
- Link、Command、表示など必要な検証結果と未確認事項が明記されている。
